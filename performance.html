Performance and tuning

How to measure, profile, and tune FPU pipelines for maximum sustained throughput.

On this page

  2. Profiling with fputool stats

Measuring performance

FPU performance is reported in three units:

MetricMeaningTool
Ttok/sTokens processed per second across the whole device.fputool probe
Ms tok/s/lanePer-lane token rate — use this to compare stages.fputool stats
p99 flow latencyEnd-to-end latency from source to sink, 99th percentile.fputool trace

Always size benchmarks to run for at least 30 seconds. The FPU has almost no warm-up cost — utilization is flat from the first token — but short runs exaggerate I/O jitter from the host.

Profiling with fputool stats

fputool stats enrich.gbit --duration=30s
Stage         Core  Lane  Rate (Mtok/s)  QDepth util  Kernel time
upper            0     1     312.4         14%         38 ns
drop             1     0     312.4         71%  ◄      61 ns
w(4096)          1     3     311.9           2%         12 ns
count            2     0     300.1          88%  ◄     104 ns

Flow summary: 301.8 Mtok/s sustained, 0 drops, p99 latency 1.14 µs

Stages marked ◄ are the pacing bottleneck — the rest of the pipeline can go no faster than they do. The QDepth util column tells you whether a slow stage is starving (low) or blocking its neighbors (high).

Common bottlenecks

1. Kernel-bound stages

If kernel time dominates, split the kernel into two stages along its internal pipeline boundary — the fabric hop is cheap (18 ns) compared to a deeper combinational kernel.

2. Fan-in thundering herds

A reduce stage with many upstream channels serializes arriving tokens. Insert a partial reduction per lane so each reducer channel receives pre-merged data: 

--> tee {
      branch 0 --> reduce partial { kernel = "count64_lane" } --> partials,
      branch 1 --> reduce partial { kernel = "count64_lane" } --> partials,
     }
--> reduce count { kernel = "count64_merge" } --> sink metrics;

3. Host-side pacing

Often the FPU isn't the bottleneck — the host feeding it is. Check fputool probe while running: if utilizing below 90% and no stage shows high queue utilization, look at your feed.stream() loop size and DMA descriptor batching first.

Tuning checklist

  • ☐ Set every window stage to the smallest size that fits your algorithm — queue memory is a shared resource.
  • ☐ Batch DMA descriptors to at least 8 KB per transfer.
  • ☐ Pin the critical path to cores with a short hop path (see fputool visualize).
  • ☐ Persuade the placer to co-locate fan-out stages with their consumers: place near constraints.
  • ☐ Re-run fputool build after every change and diff the closure report — placement is not incremental.
warning
Warning
Over-constrained placements can leave fabric channels idle and reduce peak throughput. Only pin the stages on your measured critical path.
