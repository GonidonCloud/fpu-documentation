Performance analysis

A reliable benchmark

FPU launches are asynchronous. Timing only the Python call measures enqueue time, not device execution. Warm up the executable, synchronize before starting the clock, run enough iterations to smooth host jitter, and wait for the final result before stopping it. 

import time
import flowkit as fk

batch_size = 64
warmup_iterations = 10
measure_iterations = 100

for _ in range(warmup_iterations):
    output = program(x, weights, bias)
output.block_until_ready()

start = time.perf_counter()
for _ in range(measure_iterations):
    output = program(x, weights, bias)
output.block_until_ready()
elapsed = time.perf_counter() - start

samples_per_second = batch_size * measure_iterations / elapsed
print(f"Throughput: {samples_per_second:.1f} samples/s")
print(f"Mean step:  {elapsed / measure_iterations * 1000:.3f} ms")

Keep inputs on device unless host transfer is part of the service path being measured. Report batch shape, dtype, compiler version, target, power mode, and whether result retrieval is included. Run the benchmark at least three times and retain the spread, not just the best result.

!
The simulator is not a benchmark target
fpu-sim validates functionality. Its execution time reflects the host CPU running the simulation and has no predictive relationship with FPU throughput.

Throughput and latency are separate objectives. Larger batches can improve tensor efficiency while worsening queueing delay. Set a service-level latency limit first, then optimize throughput within that limit.

Arithmetic intensity

Arithmetic intensity is the number of arithmetic operations divided by bytes moved from memory. Low-intensity operations such as standalone casts and elementwise chains are often limited by bandwidth. Fusion can remove intermediate transfers and increase useful work per byte. Dense matrix operations generally offer more opportunity to keep the matrix array occupied, provided their tiles fit local memory well.

Profiler workflow

Capture a bounded region rather than an entire training job:

fputool profile \
  --output ./profiles/linear-relu \
  --steps 100:200 \
  python train.py

Generate a text summary and inspect the timeline:

fputool report ./profiles/linear-relu
fputool timeline ./profiles/linear-relu --output timeline.html

A summary highlights the dominant activities for the captured interval:

Percentages for different engines can overlap because they execute concurrently. Use the timeline to distinguish serial dependencies from simultaneous activity.

Reading bottlenecks

Low compute occupancy with high memory traffic

  • Fuse compatible elementwise operations into their producer or consumer.
  • Use a narrower storage dtype after validating accuracy.
  • Increase batch or tile dimensions so each transferred operand supports more math.
  • Keep weights and activations on device between program invocations.

High compute occupancy but poor application throughput

  • Check for excessive host-to-device copies included in the application step.
  • Look for shape changes that trigger additional compilations.
  • Verify that matrix dimensions map efficiently to tiles; test nearby dimensions.
  • Confirm that the profiler region and application benchmark measure the same work.

Device idle gaps

  • Prefetch and preprocess the next batch while the current program executes.
  • Reuse compiled executables instead of compiling inside the serving loop.
  • Batch small requests within the allowed latency budget.
  • Move application logging and result serialization out of the critical path.

HBM capacity pressure

Read program.resource_report to identify live tensors at the peak. Reduce activation lifetime through rematerialization, shard parameters or optimizer state, or use pipeline stages. Increasing SRAM requests without reducing live HBM values does not solve an HBM capacity problem.

Workgroup scaling

Compare throughput per device as the workgroup grows. A collective that runs after every small layer can dominate an otherwise efficient data-parallel step. Increase local work, overlap independent reductions with compute, and place communicating partitions on nearby links. 

# Efficiency relative to a measured one-device baseline
scaling_efficiency = workgroup_throughput / (baseline_throughput * device_count)

Measure the slowest device, not only the aggregate. A collective completes at the pace of its slowest participant, so host preprocessing jitter or a degraded FlowMesh link can appear as workgroup-wide idle time. Use fputool links to check link health before changing model partitioning.

Optimization checklist

  1. Freeze correctness. Keep a reference output and accuracy check for every precision or graph change.
  2. Stabilize inputs. Use fixed shape buckets, preloaded parameters, and a warmed executable.
  3. Synchronize measurement. Separate host time, device time, transfers, and end-to-end service time.
  4. Address the largest item. Change the operation or transfer that dominates the captured interval.
  5. Recheck the profile. A new bottleneck can appear after the original one is removed.
  6. Validate under load. Test production request concurrency and multi-device health before rollout.
