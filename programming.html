Programming with FlowLang

The FPU's programming model: pipelines, stages, kernels, and the host runtime.

The programming model

Programs for the FPU are pipelines: directed graphs of stages whose data dependencies are known before the program runs. You describe what each stage does; the toolchain decides where and when it executes. This division is why FPU programs have no data races by construction — two stages never run "simultaneously" in a way that touches the same token.

FlowLang basics

FlowLang is GonidonCloud's pipeline description language. A program is a list of stage declarations and wiring rules: 

// declare reusable stage templates
stage map upper      { kernel = "utf8_upper"; }
stage filter drop    { kernel = "predicate_drop"; predicate = f.score < 0.5; }
stage window w(4096) { kernel = "ringbuffer_win"; }
stage reduce count   { kernel = "count64"; }

// wire them into a top-level flow named "enrich"
flow enrich {
  source feed_in
    --> upper
    --> drop
    --> w
    --> count
    --> sink feature_out;
}

Language elements at a glance:

ElementPurpose
source / sinkTyped boundaries: host memory, FlowLink ports, files, or sockets.
map, filter, window, reduce, teeStage templates covering the common streaming patterns.
kernelThe executable body of a stage (see below).
branch NNamed output of a multi-output stage such as tee.

Kernels

A kernel is the actual computation inside a stage. Most pipelines use kernels from the standard kernel library (over 400 kernels: parsing, math, hashing, codecs, ML feature transforms). For custom logic, write kernels in GDK-C, a strictly bounded C subset: 

// Kernel: saturating 16-bit FIR filter, fixed taps.
kernel fir16(input tok : s16x8, output out : s16x8) {
  state s16 coeffs[8] = { 3, 7, 15, 31, 31, 15, 7, 3 };  // placed in flow memory
  s32 acc = 0;
  for (i in 0..8) {
    acc = sat_add32(acc, coeffs[i] * tok.lane[i]);
  }
  out.lane = saturate_s16x8(acc >> 6);
  emit out;
}

GDK-C guarantees:

  • Bounded loops — every loop trip count is known at compile time; there are no data-dependent hangs on silicon.
  • No pointers outside namespace — memory access is checked against the stage's assigned regions.
  • Deterministic latency — the compiler reports worst-case cycles per token.
info
Note
If you can express your transform in the standard library, prefer it. Library kernels are hand-pipelined and typically 20–40% faster than first-draft GDK-C.

Host runtime API

Pipelines are driven from the host with fpu-python, the primary runtime binding (C and Rust bindings ship alongside): 

import fpu

dev = fpu.open(device=0)

pipeline = fpu.load_bitstream("enrich.gbit", device=dev)
feed     = pipeline.source("feed_in",  buffer_size=1 << 20)
take     = pipeline.sink("feature_out")

pipeline.run()          # non-blocking; hardware starts flowing

feed.stream(my_data)    # push tokens
out = take.drain()      # pull results

pipeline.stop()
fpu.close(dev)

The runtime never copies data across the PCIe boundary unless the pipeline requests it — tokens enter device HBM via direct DMA descriptors.

Placement and constraints

The placer assigns stages to cores and flows to fabric channels. It optimizes for routability first, then hop count on the critical path. For latency-sensitive pipelines you can pin stages manually: 

constraints {
  place upper on core 0;
  place w     on core 1, lane 3;
  flow feed_in route min_hop;
  locate sink feature_out at port FlowLink[1];
}

Verify any placement with fputool visualize enrich.gbit, which renders the mapped pipeline as an SVG annotated with hop counts and queue depths.
