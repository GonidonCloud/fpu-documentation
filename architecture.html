Inside an FPU

How compiled tensor graphs map onto compute clusters, local memory, and a multi-device workgroup.

Execution model

An FPU executes a compiled command stream, not a sequence of individually dispatched framework operators. The Flow compiler analyzes the complete graph, fuses compatible operations, divides tensors into tiles, and reserves memory for inputs, outputs, and intermediates. The resulting Flow binary (.flb) contains device code and a declarative resource plan.

At run time, the host writes argument descriptors and starts the program. A scalar sequencer in each cluster issues work to its tensor engines and DMA engines. Because dependencies are encoded in the command stream, independent compute and transfer operations can proceed in parallel without further host involvement.

Compilation is shape-aware
Changing a tensor shape can change tiling, memory layout, or the number of devices required. Compile a separate executable for each shape bucket used in production.

Clusters and tensor engines

A device is divided into compute clusters. The FPU M2 reference configuration has four clusters, each containing two tensor engines, a scalar sequencer, DMA engines, and a local SRAM partition. Clusters exchange tiles through the on-chip crossbar; they do not share a cache-coherent view of local memory.

Each tensor engine combines three execution resources:

ResourceWork performedTypical operations
Matrix arrayDense products on two-dimensional tilesMatmul, convolution, attention projections
Vector lanesElementwise and reduction work across tilesActivation, normalization, softmax, cast
Scalar sequencerBounded control flow and address generationLoop counters, descriptors, dependency checks

Tiling is primarily a compiler concern. A logical operation such as a 4096 × 4096 matrix multiplication is decomposed into smaller matrix operations whose operands fit in cluster SRAM. The compiler chooses the tile dimensions and layout together; changing only one can make an otherwise valid schedule inefficient.

Memory hierarchy

FPU memory is explicitly managed by compiled schedules. Values are copied between levels by DMA engines; there is no assumption that a frequently used value will be retained automatically. This makes capacity visible and transfer costs measurable.

LevelM2 reference sizeVisibilityPrimary role
Engine registersAllocated by the compilerOne tensor engineImmediate matrix and vector operands
Cluster SRAM64 MB per clusterEngines in one clusterTiles, small weights, fusion intermediates
Device HBM96 GB per deviceAll clusters on the deviceParameters, activations, optimizer state

Buffers and lifetimes

FlowKit device arrays own HBM allocations until they are released. Within a compiled program, the compiler can reuse an intermediate allocation as soon as its last consumer finishes. Live values that do not fit must be spilled to HBM, recomputed, or sharded across devices. The compiler reports peak memory by level so these choices can be evaluated before execution.

Numeric formats

Storage type and accumulation type are separate choices. Narrow storage reduces HBM traffic and SRAM footprint; wider accumulation limits rounding error in reductions.

Quantized operations carry per-tensor or per-channel scales and zero points. The compiler preserves these parameters through fusion where possible and inserts an explicit conversion when a consumer requires a different format.

FlowMesh interconnect

FlowMesh connects FPUs into a workgroup. Links can be arranged as a ring or attached to a switched fabric. A workgroup has a logical topology used by the compiler and runtime; physical cabling is discovered independently by the management service.

Collective operations move activations, gradients, and parameters without staging them in host memory. Common primitives include all_sum, all_gather, reduce_scatter, and point-to-point send/recv. The compiler can overlap a collective on one partition with computation on another when their dependencies allow it. 

# Logical four-device axis used by a compiled program
mesh = fk.Mesh(devices=[0, 1, 2, 3], axis="data")

# Each device contributes a partial gradient; all receive the sum.
global_gradient = fk.collectives.all_sum(local_gradient, mesh=mesh)

Isolation and reliability

  • Queue isolation. A runtime context can access only its assigned device queues and HBM allocations.
  • Memory clearing. Allocations are cleared before ownership moves between contexts.
  • Signed executables. Production devices can require signed Flow binaries and firmware.
  • Health monitoring. Correctable memory events, link retries, and thermal state are exported through fputool.
  • Job recovery. The runtime reports the failed device and collective epoch so an application can restore its most recent checkpoint.
